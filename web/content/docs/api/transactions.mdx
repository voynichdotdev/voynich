---
title: Transactions
description: How the Voynich HTTP API builds a transaction, who signs it and in what order, how it is submitted in both modes, and how its status is followed.
---

Every change to the chain that the API offers goes through the same three steps: a build route returns an unsigned transaction, the signers sign it, and it is submitted and followed here. The API never holds a key of the caller's.

<Steps>
<Step title="Build">

Call one of the twenty-eight build routes. It returns a [Build](#build).

</Step>
<Step title="Sign">

Deserialize `transactionBase64`, sign with the wallet, then with any other key in `requiredSigners`.

</Step>
<Step title="Submit">

Send the signed bytes, or the signature of a transaction the wallet sent itself, to `POST /v1/transactions/submit`.

</Step>
<Step title="Follow">

Read `GET /v1/transactions/{id}` until the status is `confirmed`, `finalized`, `failed` or `expired`.

</Step>
</Steps>

## Build

What every build route returns.

<Fields>
<Field name="id" type="string" required>
The build's id. It names the transaction in `POST /v1/transactions/submit` and `GET /v1/transactions/{id}`.
</Field>
<Field name="transactionBase64" type="base64" required>
The unsigned transaction: a version 0 Solana transaction whose fee payer is the request's `wallet`. It opens with two Compute Budget instructions, a unit limit measured for this transaction and a unit price, followed by the action's instructions.
</Field>
<Field name="blockhash" type="string" required>
The recent blockhash the transaction carries.
</Field>
<Field name="lastValidBlockHeight" type="integer" required>
The last block height at which that blockhash lands.
</Field>
<Field name="cosigned" type="boolean" required>
Whether the API adds a signature of its own. `false` for every action.
</Field>
<Field name="action" type="string" required>
The instruction built. One of the twenty-eight [actions](#actions).
</Field>
<Field name="requiredSigners" type="array of addresses" required>
Every key that signs the transaction, the request's `wallet` among them.
</Field>
<Field name="fixture" type="boolean" required>
`false` for a build made against a cluster.
</Field>
<Field name="addresses" type="object" required>
The accounts the action is about. Each is present when the action has it: `model` (address), `call` (address), `receipt` (address), `weights` (array of addresses), `uploadKey` (address), `bounty` (address), `attempt` (address), `measurement` (address), `policy` (address), `grant` (address), `modelVersion` (address), `session` (address).
</Field>
</Fields>

The API simulates the transaction before it returns the Build, so a Build in hand passed simulation at the slot it was built.

### Errors from a build

A build route reads the accounts it needs, assembles the transaction and simulates it. Beside the [errors every POST route shares](/docs/api/overview#on-every-post-route), it can answer:

| Code | Stage | When |
| --- | --- | --- |
| `MODEL_NOT_FOUND`, `ENCLAVE_NOT_FOUND`, `CALL_NOT_FOUND` | `read` | An account the request names does not exist on chain. |
| One of the codes in the next table | `simulation` | The `voynich` program refused the transaction in simulation with an error the API has its own code for. |
| `INSUFFICIENT_FUNDS` | `simulation` | The wallet holds less than the transaction needs. See [Funding](#funding). |
| `SIMULATION_FAILED` | `simulation` | The transaction failed in simulation for any other reason, such as another program error. |
| `PROGRAM_REFUSED` | `build` | The transaction cannot be built as one transaction: it is larger than 1,104 bytes, or its signers are not the ones expected. |

When a program raised the error, the envelope's `programError` names the program, the error and its number.

### Funding

`INSUFFICIENT_FUNDS` is not retryable, and its envelope carries [`funding`](/docs/api/overview#the-error-envelope) with the amounts. The API answers it when the simulation fails for lack of lamports and the wallet's balance is below `required`, which is the transaction's fee plus what the action moves or puts into rent:

| `action` | Lamports beside the fee |
| --- | --- |
| `create_model` | The Model account's rent (8,192 bytes) and `uploadFundingLamports`. |
| `grant_by_owner` | The Grant account's rent, when the Grant does not exist yet. |
| `open_call`, price in SOL | The Call account's rent and the price. |
| `open_call`, price in a mint | The Call account's rent, and the rent of the Call's token account when it does not exist yet. |
| `settle_metered_call` | The 423-byte metered Receipt account's rent, plus any missing SPL associated token accounts for owner, operator, fee recipient, or caller. |
| `publish_measurement` | The 366-byte Measurement PDA's rent. |
| `set_policy` | The 1,770-byte Policy PDA's rent, when the Policy does not exist yet. |
| `begin_version` | The 8,192-byte ModelVersion PDA's rent. |
| `open_session` | The 186-byte Session PDA's rent, `budget` (for SOL sessions), any `delegateGasLamports`, and SPL escrow ATA rent for SPL sessions. |
| any other | None. For `write_weights` the wallet is the upload key, which pays the fee from the upload funding. |

`required` is at least the fee plus the rent-exempt minimum of an account with no data. When the payment would leave the wallet below that minimum, the minimum is added to `required`. Lamport amounts carry `mint: null`.

For `open_call` with a price in a mint, the API first reads the caller's associated token account for the mint. When it holds less than the price, the build answers `INSUFFICIENT_FUNDS` before any transaction is assembled, with `funding.mint` the price's mint and the amounts in its base units.

| --- | --- |
| `ModelNotUploading` | `MODEL_NOT_UPLOADING` |
| `ModelNotSealed`, `ModelNotLive` | `MODEL_NOT_LIVE` |
| `InvalidAttestation` | `ENCLAVE_EXPIRED` |
| `MeasurementNotAllowed` | `MEASUREMENT_NOT_ALLOWED` |
| `GrantRequired` | `GRANT_REQUIRED` |
| `CallNotOpen` | `CALL_NOT_OPEN` |
| `CallDeadlinePassed` | `CALL_DEADLINE_PASSED` |
| `CallNotRefundable` | `CALL_NOT_REFUNDABLE` |
| `UploadIncomplete` | `UPLOAD_INCOMPLETE` |
| `CiphertextHashMismatch` | `CIPHERTEXT_HASH_MISMATCH` |
| `InvalidWrappedKey` | `INVALID_ENVELOPE` |
| `InvalidMeasurement` | `INVALID_MEASUREMENT` |
| `InvalidPolicy` | `INVALID_POLICY` |
| `PolicyCallerDenied` | `POLICY_CALLER_DENIED` |
| `PolicyOperatorDenied` | `POLICY_OPERATOR_DENIED` |
| `PolicyRequired` | `POLICY_REQUIRED` |

Every other error of the program arrives as `SIMULATION_FAILED` with its name in `programError.name`. They are listed in [Program errors](/docs/program/errors).

## Signing

The wallet signs first. A wallet can add instructions of its own to a transaction before it signs, so every other key signs the copy the wallet returned, not the bytes of the Build.

<Steps>
<Step title="The wallet">

The request's `wallet` signs `transactionBase64` as the fee payer. For `write_weights` the `wallet` is the upload key, and it is the only signer.

</Step>
<Step title="The other required signers">

For `create_model` and `seal_model` the upload key signs the transaction the wallet returned.

</Step>
<Step title="Serialize">

The signed transaction is at most 1,232 bytes. The Build leaves 128 bytes of that for what the wallet adds.

</Step>
</Steps>

A Build is good until the block height passes `lastValidBlockHeight`. After that, build again.

## `POST /v1/transactions/submit`

Hands a signed Build back to the API. The body takes one of two shapes, chosen by `mode`.

### `relay`: the API sends the transaction

```http
POST /v1/transactions/submit
Content-Type: application/json

{
  "mode": "relay",
  "buildId": "<id of the Build>",
  "signedTransactionBase64": "<signed transaction, base64>",
  "idempotencyKey": "<1 to 128 characters>"
}
```

<Fields>
<Field name="mode" type="string" required>
`relay`.
</Field>
<Field name="buildId" type="string" required>
The Build's `id`.
</Field>
<Field name="signedTransactionBase64" type="base64" required>
The transaction with every required signature.
</Field>
<Field name="idempotencyKey" type="string, 1 to 128 characters" required>
A key that names this submission. See [Idempotency keys](#idempotency-keys).
</Field>
</Fields>

The API checks the signed copy against the Build, simulates the exact bytes with their signatures verified, records them, and sends them to the cluster. Each later read of the status sends the same bytes again while their blockhash is valid, so the transaction lands once or not at all.

The signed copy is accepted when:

- it deserializes as a transaction of at most 1,232 bytes
- its fee payer is the Build's `wallet`, with a valid signature
- it contains an instruction of the `voynich` program
- every other instruction belongs to the Compute Budget, System, SPL Token, Associated Token Account or Lighthouse program

### `wallet-sent`: the wallet sent the transaction

```http
POST /v1/transactions/submit
Content-Type: application/json

{
  "mode": "wallet-sent",
  "buildId": "<id of the Build>",
  "signature": "<transaction signature, base58>",
  "idempotencyKey": "<1 to 128 characters>"
}
```

<Fields>
<Field name="mode" type="string" required>
`wallet-sent`.
</Field>
<Field name="buildId" type="string" required>
The Build's `id`.
</Field>
<Field name="signature" type="transaction signature" required>
The signature of the transaction the wallet sent to the cluster.
</Field>
<Field name="idempotencyKey" type="string, 1 to 128 characters" required>
A key that names this submission.
</Field>
</Fields>

The API records the signature and reads its status from the cluster. It sends nothing itself.

### Response

Both modes return a [TxStatus](#txstatus) with `status` `submitted` and the transaction's `signature`. The same TxStatus goes out on [`GET /v1/events`](/docs/api/overview#event-streams) as `transaction.updated`.

### Errors

| Code | Stage | When |
| --- | --- | --- |
| `VALIDATION_ERROR` | `validation` | The body is neither of the two shapes. |
| `NOT_FOUND` | `build` | No Build has this `buildId`. Build again. |
| `IDEMPOTENCY_CONFLICT` | `send` | The Build was already submitted with another idempotency key. |
| `PROGRAM_REFUSED` | `wallet` | `relay` only. The signed copy is not accepted: one of the four conditions above does not hold. `message` says which. |
| A code from [Errors from a build](#errors-from-a-build), or `SIMULATION_FAILED` | `simulation` | `relay` only. The signed bytes failed in simulation, a missing or invalid signature included. |

### Idempotency keys

A Build is submitted once. `idempotencyKey` makes a repeated request safe:

- The same `buildId` with the same key returns the TxStatus of the first submission, as it stands now. Nothing is sent twice.
- The same `buildId` with a different key is refused with `IDEMPOTENCY_CONFLICT` at stage `send`.

The key is any string of 1 to 128 characters. The Build's `id` serves as one.

## `GET /v1/transactions/{id}`

Reads the status of a Build. `{id}` is the Build's `id`. Each read of a submitted Build looks the transaction up on the cluster once and returns the result. A Build that was not submitted reads `built`.

Returns a [TxStatus](#txstatus).

| Code | Stage | When |
| --- | --- | --- |
| `NOT_FOUND` | `confirmation` | No Build has this id. |

Next: once the status is `confirmed` or `finalized`, read what the transaction changed from its own route, such as `GET /v1/models/{id}` or `GET /v1/calls/{id}`.

## TxStatus

<Fields>
<Field name="id" type="string" required>
The Build's `id`.
</Field>
<Field name="status" type="string" required>
One of the seven [statuses](#statuses).
</Field>
<Field name="signature" type="transaction signature">
The transaction's signature, once it is submitted.
</Field>
<Field name="error" type="TxFailure">
A [TxFailure](#txfailure), when the status is `failed` or `expired`.
</Field>
</Fields>

### Statuses

| Status | The transaction |
| --- | --- |
| `built` | was built and has not been submitted. |
| `submitted` | was taken by the API and the cluster reports no confirmation of it. |
| `unconfirmed` | was sent by the wallet, and the cluster reports nothing for its signature after the Build's `lastValidBlockHeight`. The API keeps reading it. |
| `confirmed` | is confirmed by the cluster. |
| `finalized` | is finalized by the cluster. |
| `failed` | landed and the cluster reports an error for it. `error` says which. |
| `expired` | was sent by the API and its blockhash expired before it landed. Nothing was spent. `error.nextStep` is to build it again. |

`confirmed`, `finalized`, `failed` and `expired` are final for a client that follows a transaction. A `confirmed` transaction reads `finalized` on a later read.

## TxFailure

<Fields>
<Field name="stage" type="string" required>
Where the transaction failed. One of the six stages below.
</Field>
<Field name="message" type="string" required>
A sentence that can be shown to a person.
</Field>
<Field name="nextStep" type="string">
What to do next, when the API has something to say.
</Field>
<Field name="retryable" type="boolean" required>
Whether trying again can succeed.
</Field>
<Field name="program" type="object">
The program that raised the error: `address` (address), `code` (its number, or `null`) and `name` (its name, or `null`).
</Field>
</Fields>

| Stage | The transaction failed | In the error envelope it is stage |
| --- | --- | --- |
| `build` | while it was built, or its Build is unknown | `build` |
| `wallet-rejected` | because the wallet declined to sign | `wallet` |
| `wallet-changed` | because the copy the wallet signed is not accepted | `wallet` |
| `simulation` | in simulation | `simulation` |
| `send` | while it was sent | `send` |
| `confirm` | on the cluster, or by expiring | `confirmation` |

A TxStatus read from the API carries stage `confirm`. The other stages reach a client as the `stage` of an [error envelope](/docs/api/overview#the-error-envelope) from a build route or from `POST /v1/transactions/submit`.
